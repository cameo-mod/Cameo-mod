## Reassessment summary

The supplied review is directionally strong: it correctly identifies integration debt, stale summaries, red structural gates, wide AI roster omissions, and the danger of turning every diagnostic count into a bulk content edit. Its major numeric findings reproduce against the snapshot reports.

Corrections and constraints:

1. **CI is described too narrowly.** The current workflow runs `make check-scripts` and `make test`; `test` depends on `all`, so the path includes compilation and MiniYAML validation. The real gap is that the normal PR workflow does not run the repository’s NUnit tests, Python test suite, or the major Cameo-specific audits. The job label says .NET 6 while setup-dotnet requests 10.0.x; validate the intended SDK before changing that setup.
2. **The CI proposal is not authorized by current workflow rules.** docs/WORKFLOW.md and CLAUDE.md say not to enable or replace CI unless a human explicitly requests it. Treat branch protection as an administrator decision and CI expansion as a proposal requiring that ruling. This reassessment is not authorization to change either setting.
3. **“Violation” and “regression” are not synonyms for “bug.”** Formula, upgrade-power, elite, roster, palette, leak, orphan, asset, and clone reports are triage queues. Assign an owner and intent before changing rules or deleting content. In particular, the 2.0x power budget is an audit threshold; the report itself says its maximum-product model ignores mutual exclusion and reachability.
4. **AI “unwired” is a measured wiring condition, not a mandate to add 638 production entries.** The latest AI report sums to 638 across 26 pool factions. First decide which actors are active, reachable, sensible for the bot, and intentionally excluded.
5. **The eight-commit engine-freshness count is not a fresh fetch guarantee.** The report itself distinguishes commit dates from fetch dates. Re-fetch the authoritative upstream before deciding whether any of those commits remain missing or applicable.
6. **Repository-size language is qualitative.** The asset audit verifies 127 over-budget PNGs and 3,628 non-conforming WAVs; it does not, by itself, quantify clone time, runtime memory, or package-size improvement.
7. **The design sections are proposals, not defects or binding law.** Universal registries, a single defining faction mechanic, doctrine choices, crossover modes, map objectives, information warfare, UI/Codex work, and a faction-coherence league need prototypes and player evidence. They should not be implemented as a single large feature wave.

### Immediate sequence and dependencies

1. **Phase 0 first:** the stale summary and asynchronous branch work make a clean evidence baseline the prerequisite for reliable triage.
2. **Phase 1 decision in parallel:** branch protection is an admin setting; CI changes are paused until explicitly authorized. Do not let lack of CI authorization block safe local audit regeneration.
3. **Phase 2 first queue:** fix the smallest proven regressions and the BOM; do not migrate the full weapon corpus at once. Re-run only the affected audits after each bounded batch.
4. **Phase 3 player-visible queue:** finish active Garrison P3 code validation separately; then refresh the garrison audit and handle remaining weapon/actor cases as new scoped work. Resolve dead upgrades and rank gating with tests before deleting content.
5. **Phase 4 AI pilot:** choose a small set spanning a classic faction, a modern faction, and one content-pack faction. Compare derived roles against existing AI production and require human approval before widening.
6. **Phase 5 balance queue:** reachability modeling precedes any response to the 828 power-threshold count. Release lineage and weapon-shape cleanup can share provenance tooling but must retain separate acceptance metrics.
7. **Phase 6 migration queue:** ContentPack/installer correctness precedes optional asset packaging. Shared Python helpers follow tests around the individual high-value tools.
8. **Phase 7–8 only after stable inputs:** add user-facing semantics from the vetted schema; treat the larger doctrine/crossover ideas as experiments, not prerequisites for a coherent base game.

## Long-term design direction, made testable

The review’s sections 30–40 are valuable as a north star, but should be translated into constrained pilots:

- **Semantic registry:** begin with actor role, tech tier, armor, weapon delivery, target role, mobility, economy role and special constraints. Derive from resolved rules where possible; store provenance and explicit exceptions for the rest. Consumers include AI, balance, UI, Codex and maps, but each consumer adopts one at a time.
- **Faction doctrine:** prototype a compact faction profile with tempo, information, mobility, army shape, strengths, weaknesses and signature mechanic. Treat “one defining mechanic” as a review prompt, not a rule that forces every faction into a single gimmick.
- **Doctrine/crossover:** keep standard competitive rosters unchanged. Prototype constrained doctrine or crossover choices in a separate optional mode, with mutually exclusive choices, visible tradeoffs, counterplay and balance ownership.
- **Maps/information:** pilot maps with a small number of legible strategic features; measure scouting, route choice and objective contesting. False signals, stealth and decoys require clear detection/counter rules.
- **UI/Codex:** generate role, tier, armor, strengths, weaknesses, movement and special mechanic descriptions from the same vetted data. Verify each tooltip against resolved rules before presenting it.
- **AI coherence league:** score faction doctrine compliance, role diversity, counter response and signature-mechanic usage alongside win/loss. Do not use win-rate alone to infer faction identity.
