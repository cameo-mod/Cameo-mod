## 2. Facts the rows rely on

- **F-1 Index-space guard in every H-1 consumer.** BotSituation (:1161), BotFogMemory (`SyncZoneGeneration` :230), BotInfluenceLayers (`EnsureSpace` :268), ScoutBot (:437) and RegionRoles (:246) all compare `(ZoneBacked, Generation[, CellCount])` and DROP their region-index state on a change, never alias ids across a generation. So the only requirement on the sliced H-1 is: every consumer sees ids of ONE generation at a time. A double buffer with an atomic swap suffices (10.4).
- **F-2 Today's publish is one tick.** `RebuildSharedOnBridgeChange` assigns Passability, AbstractDomains, NodeCells, LastBridgeSignature, Chokepoints, BridgeWatchCells, Regions, RegionGateCorridors, RegionIdByCell, RegionBarrier and then `Generation++`. The sliced H-1 must swap ALL of these in one visit and bump `Generation` last; a partial swap would give RegionRoles a region list from one cut and `GetRegionGateCorridor` indices from another.
- **F-3 Adopt order and cache drop.** A non-owner bot adopts at its own tick, before any region id is read (TacticalMap :392-401), and `ResetPerBaseCaches` (:504) drops territory, doors, wall, front, useful set, corridors, high-ground and `regionOwners` (set to `[]`, refilled by the next 250-tick ownership tally; `RegionOwner` answers null meanwhile and RegionRoles treats null as no owner, :335-343). So the H-2 and H-3 jobs take H-1's `Generation` as an L input (restart on change, 10.4) and a stale H-2/H-3 result is never published over a newer cut.
- **F-4 Gates already exist.** `TopologyReady` / `Generation >= 0` gate RegionRoles (:200, :222), BotSituation (:1152 falls back to the grid RegionMemory) and ScaleTargets (:417, `useTerritory`). A Starved job with NO previous generation therefore degrades to today's start-of-game behavior (grid regions; empty territory).
- **F-5 BotRng.** `ResetPerBaseCaches` draws 5 BotRng values per call (D078-D081, R10). The sliced H-1 keeps exactly ONE reset per published generation per bot (at its adopt); two bridge changes coalesced into one publish therefore give one reset where the synchronous path gives two: a declared decision change, measured in T2/T5, never a hidden one. Test: stream position equal at N=1 for a stable generation.
- **F-6 Dead-compute finding (outside STAGGER-06, for Opus/Leader).** The useful-chokepoint, corridor, high-ground, wall/front/door outputs have no behavior-changing reader at 6f1f7dfd6 (section 1). If that is right, the cheapest perf win is NOT to slice them but to skip them per bot (a TacticalMap trait flag, no behavior change, same result for every consumer that exists). This is a separate change; it does not block the table. Haiku: please confirm the zero-caller list with an independent `git grep`.

## 3. Consumer table

Columns: id | job | consumer (file:line at 6f1f7dfd6) | reads | consumer cadence | tolerated staleness (ticks from the triggering change to publish, today's lag in brackets) | slicing budget (tolerance minus today's lag) | rule while Starved or older than tolerance | element-level revalidation | status | test.

Proposed tolerances: TOL1 = 300 (H-1), TOL2 = 500 (H-2), TOL3 = 250 (H-3).
- TOL1: H-1 is triggered by a bridge signature change detected by the 50-tick recheck (`TopologyRecheckInterval`, today lag up to 50 plus adoption at the next bot tick); the slowest H-1 consumer cycle is RegionRoles / ownership at 250; 250 + 50 = 300, so no consumer sees more than one extra stale cycle. Movement itself uses the live engine pathfinder, not these ids.
- TOL2: H-2 is polled every `TerritoryRefreshInterval` = 250 and only rebuilds when the base moved or the remembered-enemy-building count changed; two poll cycles = 500, about a fifth of `ScoutStaleTicks` 2500, the time scale of its only reader.
- TOL3: H-3 runs every `UsefulRefreshInterval` = 125; two cycles = 250.

## 4. Result

- **H-1: ENABLE** (subject to the 10.2 bound <= 250 and to the atomic swap of F-2). Eight external rows and one in-module row, all with a stale rule that keeps the previous generation and an existing generation guard.
- **H-2: ENABLE for one consumer** (ScaleTargets, A2-2a) if the 10.2 bound <= 250; every other H-2 reader has no caller (A2-2b).
- **H-3: in-module consumer only** (A2-3a); no external consumer, so it adds no behavior change; slicing it is a perf-only, low priority change, and F-6 suggests skipping it per bot instead. By the rule of 10.4 a job kind needs a consumer row: it has A2-3a, nothing more.

- **Not decided here:** the D-4 constants (R_max, StarveBackoff, VisitCap, floors); the J4 job specs; the 10.2 bound per job (measured at step 7 after A-5).
